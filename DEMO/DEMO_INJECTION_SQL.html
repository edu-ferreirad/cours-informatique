🗄️ Démo : injection SQL

Connexion — Espace Administration (démo)

Ce formulaire simule (sans vraie base de données) un site mal protégé contre les injections SQL. Essaie de te connecter normalement, puis essaie l'astuce indiquée en bas.
Requête envoyée à la base de données (simulée) :
💡 À essayer dans le champ mot de passe : ' OR '1'='1

Le problème

Ce formulaire fabrique la requête en collant directement ce que tu tapes dans le texte de la commande envoyée à la base de données. Si tu tapes du code SQL au lieu d'un mot de passe normal, ce code SQL est exécuté tel quel.

Comparaison

❌ Ce que fait cette démo (vulnérable)
requete = "SELECT * FROM users WHERE user='" + identifiant + "' AND pass='" + motdepasse + "'" // Si motdepasse = ' OR '1'='1 // -> ... AND pass='' OR '1'='1' // '1'='1' est TOUJOURS vrai : accès accordé // à n'importe qui, sans connaître le mot // de passe !
✅ Ce que fait un vrai site bien codé
requete = "SELECT * FROM users WHERE user=? AND pass=?" executer(requete, [identifiant, motdepasse]) // Les valeurs saisies sont toujours traitées // comme de simples DONNÉES, jamais comme // du code — impossible d'en sortir avec // une apostrophe.

Les règles à retenir

1. Ne jamais construire une requête en collant directement le texte saisi par l'utilisateur.
2. Utiliser des "requêtes préparées" (paramétrées) — la méthode standard depuis des décennies.
3. Ce principe dépasse le SQL : ne jamais faire confiance à une entrée utilisateur, nulle part.
4. Ce genre de faille a permis de vraies fuites massives de données dans le monde réel — ce n'est pas juste théorique.

Mentions légales

Cette page est une simulation pédagogique créée dans le cadre d'un cours de cybersécurité. La "base de données" est un tableau JavaScript en dur dans la page — il n'y a aucun serveur, aucune vraie base de données, aucune requête réseau.
